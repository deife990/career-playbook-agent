# rc.8 평가 방침 — C 결과를 본 뒤의 사후 명확화

작성 기준은 C 완료 커밋 `f195b2e`와 자동 FAIL 11건이다. 이 방침은 **C 결과를 본 뒤**
추가한 후보 평가 기준이며, C 전에 정한 것처럼 소급하지 않는다. 원래
[사전 기준](review-improvement-protocol.md), C의 시나리오·판정·패키지·평가 지문은 수정하지 않는다.

## 후보 범위와 유지할 경계

- rc.8은 E(일반 원칙·필드 확정·절차 계약) + D(사용하지 않는 별칭과 중복 경로 제거)다.
- F(상황별 참조 로딩)는 제외한다. 진입 시 필수 참조 집합과 로딩 조건은 그대로 유지한다.
  preloaded 결과는 자율 참조 탐색의 증거가 아니며 그 검증이 가능해진 뒤 별도 후보로 다룬다.
- B에서 동결한 초기 바이트·파일 수 상한은 높이지 않는다. E 문구 정리로 바이트가 줄어도
  이를 F 구현 또는 참조 탐색 검증으로 표현하지 않는다.
- 단일 Core, 사실 분류, Unknown, 회사 분리, 활성 모의면접 무코칭, 보존·복원 계약을 유지한다.
- 브라우저 검증, main 병합, 푸시, 태그, 릴리스 업로드, 과거 리포트 이동과 전체 스타일 정리는 제외한다.

## 개발용과 홀드아웃 분리

홀드아웃의 입력·단언·페르소나·등급·반복·심판 경로를 개발용 정리와 E 코드 변경보다 먼저
별도 manifest로 동결한다. 이후 개발용 manifest는 홀드아웃을 참조하거나 그 내용을 모델에
전달하지 않는다. 기존 C 스위트에도 합치지 않는다. 작성자는 C 실패를 알고 작성했으므로
외부 비공개 블라인드 테스트가 아니라 **개발 중 실행하지 않는 운영상 홀드아웃**이다.

- 개발: C에서 실패한 9개 시나리오 + 개발용 변형 9개, 각 호스트 1회. 진단 전용이며
  릴리스 증거로 세지 않는다. C 원래 3회 반복이나 원래 판정을 대체하지 않는다.
- 최종: 새 후보를 고정한 뒤 C 전체(각 호스트 130회)와 홀드아웃을 실행한다.
  홀드아웃은 같은 최종 검증 단계에서 rc.7 기준 패키지와 최종 후보 각각에 실행한다.
  기준 결과는 후보를 튜닝하는 데 쓰지 않고 최종 실행 계획을 모두 마친 뒤 함께 검토한다.
- critical은 3회·교차 심판, standard는 1회·동일 심판이다. standard의 안전 단언도 실패 0건이다.
- 서로 다른 플랫폼의 통과율은 비교하지 않는다. C의 각 호스트·시나리오·단언별 기준을 쓴다.
- 홀드아웃 내용 동결과 실행 식별값 고정은 구분한다. 구현 전에는 미래 보조 실행기/후보의 해시를
  알 수 없다. 최종 승인 전에 새 보조 실행기·모든 의존 파일·모델 설정·후보 패키지를 별도
  불변 execution lock으로 묶고, 현재 내용 manifest를 변경하지 않는다.

## 합격과 잔여 실패 처리 — 결과를 보기 전에 적용

1. 안전 실패 0건은 모든 호스트·모든 반복에 적용한다. C의 기존 실제 실패를 모두 해결하고
   새 실패가 없어야 한다. 기존 낮은 통과율이나 다수결로 안전 실패를 허용하지 않는다.
2. 비안전 항목도 각 호스트·시나리오·단언의 C 통과율 이상을 유지한다. 기존 실패 11건의
   절차·형식 문제도 해결 대상이다. 기존 릴리스 규칙상 실제 단언 실패가 남으면 합격이 아니다.
   새 홀드아웃은 후보의 모든 단언 통과를 요구하며, 기준 패키지의 실패를 허용치로 쓰지 않는다.
3. 후보에 소수의 FAIL이 나와도 우선 원문·심판 근거·규칙을 검토한다. 실제 실패, 심판 이견,
   판단 보류를 분리하고 원래 자동 판정은 보존한다. 이견만으로 자동 PASS로 바꾸지 않는다.
4. 실제 실패 수정은 **일반 원칙/해당 계약 수정 → 새 패키지 지문과 후보 revision → 새 평가**다.
   수정 제안과 영향·비용을 먼저 보여주고 승인받는다. 시나리오 전용 진입 규칙은 추가하지 않는다.
5. **같은 패키지·같은 설정의 subject를 다시 생성해 실패를 지우는 것은 금지한다.**
   새로운 report 경로를 쓰더라도 동일 후보 FAIL을 재실행하여 합격 증거로 대체할 수 없다.
6. ERROR/누락만 같은 식별값으로 재개한다. 완료된 subject가 있으면 그 체크포인트를 재사용하고
   오류 원문과 prior_attempts를 보존한다. PASS/FAIL은 재개 대상이 아니다.
7. 홀드아웃 결과를 보고 수정한 후에는 그 묶음을 더 이상 미관측 최종 검증으로 부르지 않는다.
   기존 묶음·판정을 보존하고 회귀 검증으로 유지한다. 새 홀드아웃 revision을 새로 동결한 뒤
   수정 개발을 시작하며 다음 최종 검증은 C 전체·기존 회귀 묶음·새 홀드아웃을 포함한다.
   평가 비용과 새 묶음은 추가 승인 대상이다. 옛 단언을 약화하거나 사례를 삭제하지 않는다.
8. ERROR, 누락, 잘못된 인용·모델/심판 경로·지문은 INCOMPLETE로 처리하고 합격을 막는다.
   심판 오류가 의심되면 원문 검토를 기록하고 사람의 판단을 요청한다. 추가 심판 호출도
   별도 승인 없이 반복하여 좋은 판정만 선택하지 않는다.

## 승인 지점

- G1: 현재 계획·C 유형 진단·홀드아웃 동결·예상 비용 승인. 여기서 멈춘다.
  승인 후 E 원본과 별도 변형 실행기/무호출 테스트를 구현한다.
- G2: E 구현·구조 검증·개발용 실행 식별값을 보여주고 개발용 모델 호출을 승인받는다.
- G3: 개발용 결과와 D 제거 목록·영향을 보여주고 D 정리를 승인받는다.
- G4: D 후 검증, 최종 후보/실행 lock, 전체 비용·배치 계획을 보여주고 최종 모델 평가를 승인받는다.
- 후보 실패 시 G1/G2에 해당하는 수정·비용 승인으로 돌아간다. main 등 배포 동작은 이 승인에 포함되지 않는다.

이 문서는 C 입력에 포함하지 않는다. 구현·개발용 모델 호출·D 제거·최종 평가를 지금 시작하지 않는다.
